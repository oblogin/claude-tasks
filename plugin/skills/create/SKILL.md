# /task:create — новая задача через обсуждение

Скрипт плагина: `node "${CLAUDE_PLUGIN_ROOT}/scripts/tasks.mjs"` (дальше — «скрипт»). Что сказал пользователь: `$ARGUMENTS`.

**Режим.** Если в аргументах есть `--yes` или `-y` (в любом месте) — режим **без подтверждения**: убери флаг из текста запроса и работай по пометкам «С `--yes`» ниже. Иначе — обычный режим: черновик и подтверждение.

Правила — в скиле `task:format`: типы (раздел 3), поля (5), «Коротко» (7), **как написать хорошую задачу (8)**. Загрузи его, если ещё не загружен.

> **Главное правило (обычный режим): до явного «Записать» пользователя на показанный черновик в плане ничего не меняется.** Не вызывай `скрипт new`, не создавай и не правь файлы в `Docs/Tasks/` — ни ради ID, ни «черновиком со статусом draft». Номер для черновика — `скрипт new-id` (он ничего не пишет). Отказался пользователь — план остаётся как был. С `--yes` пользователь заранее разрешил запись — шаг 3 пропускается.

## 1. Понять контекст

- Посмотри план: `Docs/Tasks/Board.md` и `скрипт list --type epic`, `--type feature` — чтобы знать, куда задача может встать.
- Прочитай то, на что задача будет опираться: ADR и задачи, от которых она зависит или которые рядом в той же фиче (`скрипт show <ID>`, сами файлы). Критерии не должны противоречить принятым решениям — например, не упоминать сценарий, которого по ADR нет.
- Проверь, нет ли уже похожей задачи или идеи (`скрипт list --json`, поиск по названиям). Есть задача — скажи и предложи дополнить её вместо новой.
- **Задача из идеи** (пользователь назвал `I-…` или нашлась похожая идея) — идея становится отправной точкой: её «Что / Зачем» — начало разговора. После записи новой задачи закрой идею со ссылкой на результат: `скрипт set <I-ID> done --promoted-to <новый ID>` — скрипт сам допишет в идею строку «**Взята в план:**» со ссылкой и датой. `--log` не добавляй: журнала у идей нет, скрипт такой вызов отклонит.

## 2. Обсудить — по одному вопросу

Задавай вопросы **по одному** (варианты — через AskUserQuestion, открытые — текстом), пока не станет ясно:

1. **Что** делаем — одним предложением.
2. **Зачем** — что это даёт.
3. **Готово, когда** — проверяемое условие; из него вырастут критерии.
4. **Тип**: `task` (работа), `research` (сначала выбрать решение → ADR), `bug` (что-то сломано), `feature` (законченная возможность из нескольких задач), `epic` (крупная цель).
5. **Место в графе**: родитель (фича для задачи, эпик для фичи) и от каких задач зависит. Предложи сам по плану — пользователь подтвердит или поправит.
6. **Кто делает** (`role`) — необязательно; свободная метка, любое слово (`programmer`, `artist`, имя агента…). Готового списка ролей нет — не предлагай его.
7. **Приоритет** (`must` / `should` / `could`) и **размер** (`XS`–`L`).

Не спрашивай то, что уже понятно из слов пользователя или из плана. Часть ответов можно предложить самому одним вопросом: «Предлагаю так: … — верно?»

С `--yes` — спрашивай, только если без ответа задачу не написать: непонятно, **что** делаем, или её некуда поставить в плане. Остальное (зачем, критерии, тип, место, роль, приоритет, размер) реши сам по плану и словам пользователя.

**Слишком большая задача** (больше `L`, несколько независимых результатов, «сделать всю систему X») — предложи оформить её фичей и сразу разбить: после создания — `/task:split <F-ID>`.

## 3. Показать черновик (с `--yes` — пропусти)

Черновик — **текст в твоём ответе**, а не файл. Покажи его **целиком**, в блоке ```markdown: frontmatter и тело — «Коротко», критерии (проверяемые, по разделу 8 `task:format`), «Детали» (всё, что нужно исполнителю, чтобы не переспрашивать), «Проверка». Сводка в несколько строк вместо файла — не черновик.

- ID — из `скрипт new-id <тип> [--parent <ID>]`, с пометкой «ID выдаётся при записи». Если родительской фичи ещё нет (создаётся в этом же обсуждении), ID задачи — `<номер фичи без дефиса>-01`, например `F05-01` для `F-05`.
- Создаёшь сразу несколько элементов (фичу и её задачи) — покажи черновики всех, одно подтверждение на все.
- Сверь критерии с ADR и зависимостями, которые прочитал в шаге 1.
- `depends_on` — только задачи, не фичи и не эпики. Нужна вся фича — поставь её последнюю задачу, после которой фича готова (например, ту, что собирает результат). Статус зависимостей смотри в плане, а не предполагай.

Спроси через AskUserQuestion: **«Записать»** или **«Уточнить»**. «Уточнить» — спроси, что поменять, внеси правки и снова покажи черновик целиком. Ответ «нет» / «не надо» — ничего не пиши и не создавай.

## 4. Записать — после «Записать» (с `--yes` — сразу после шага 2)

1. `скрипт new <тип> --title "<название 2–6 слов>" --parent <ID> [--depends <ID>,<ID>] [--role <роль>] --priority <p> [--size <s>] --status <draft|ready> --json`
   - `ready` — если есть критерии и понятно, как проверить; иначе `draft`. Пустой пункт шаблона `- [ ]` критерием не считается: у `ready` без вписанных критериев `check` предупредит.
   - Скрипт сам выдаст ID, папку, имя файла и frontmatter. Ошибка — поправь аргументы.
   - Несколько элементов — сначала родитель (фича), потом её задачи. ID от `new` отличается от показанного в черновике — поправь ссылки в теле и скажи об этом в итоге.
   - Записывается ровно согласованный черновик. Скрипт отклонил что-то по сути (зависимость, родителя, поле) — не меняй это молча: объясни пользователю, предложи исправление и спроси снова. С `--yes` — исправь сам и назови исправление в итоге.
2. Открой созданный файл (`file` в ответе) и впиши согласованное тело вместо подсказок. **Удали все подсказки `<!-- … -->`**; необязательный раздел, в который нечего писать, убери («Коротко» и «Журнал» — не убирать).
3. `скрипт check` — ошибок быть не должно; предупреждения о новом файле — исправь.
4. `скрипт board` — доска обновлена.

## 5. Итог

Коротко: ID и название, статус, где в графе (родитель, от чего зависит, что будет ждать её), путь к файлу. Если задача большая — напомни про `/task:split`.

С `--yes` — дополнительно покажи записанный файл целиком (как черновик в шаге 3): пользователь его ещё не видел. Не устраивает — поправит через правку файла или `/task:replan`.
