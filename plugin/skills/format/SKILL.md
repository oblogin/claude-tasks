# Формат плана задач

Единственный источник правил для людей, агентов, команд `/task:*` и скрипта проверки. Если правило здесь не описано — его нет.

Спецификация одинакова для любого агента — программиста, геймдизайнера, девопса или любого другого. Она описывает **устройство задач и то, как с ними работать**, но не то, как делать саму работу: это знает агент. Если ты агент и тебе нужно работать с планом — начни с раздела 9.

## 1. Главные принципы

1. **Задачу понимают за несколько секунд.** Сразу под заголовком — блок «Коротко». Подробности любого объёма — ниже.
2. **У каждого факта одно место.** Зависимость пишется только в `depends_on` задачи-потребителя; принадлежность — только в `parent` ребёнка. Обратные связи, списки детей и доска вычисляются.
3. **Статус всегда правдив.** Агент, работающий по задаче, обновляет статус и журнал сразу, в том же шаге, что и работу (раздел 9).
4. **Чистый Markdown.** План читается в Obsidian без плагинов; связи — вики-ссылки `[[...]]`.
5. **Поля — по-английски, содержимое и заголовки — по-русски.** Имена и значения полей frontmatter английские; всё, что читает человек, — на русском.

## 2. Раскладка

План разложен **по иерархии**: эпик — папка, фичи — папки внутри эпика, задачи — файлы внутри фичи. Папка эпика и фичи называется так же, как её заметка.

```
Docs/Tasks/
├── Readme.md                          ← что это за папка и ссылка на этот формат
├── Board.md                           ← доска; генерируется, руками не править
├── E-01 Прототип игры/
│   ├── E-01 Прототип игры.md
│   ├── F-03 Прыжок/
│   │   ├── F-03 Прыжок.md
│   │   ├── F03-01 Гравитация и падение.md
│   │   └── F03-02 Койот-тайм для прыжка.md
│   └── F-04 …/
├── Backlog/                           ← I-001 … (идеи)
├── Adr/                               ← ADR-001 … (решения, результат research)
└── .claude-tasks/                     ← служебная: блокировка и кто взял задачу; скрыта, в git не попадает
```

Место файла задаёт его родитель (`parent`): задача лежит в папке своей фичи, фича — в папке своего эпика. Смена статуса или спринта файл не двигает. Перенос в другую фичу или эпик — только командой `tasks.mjs move` (раздел 4). Имена служебных файлов и папок `Backlog/`, `Adr/` — UpperCamelCase. Вложения (картинки, pdf) можно класть рядом с заметками и встраивать: `![[схема.png]]`.

Папка плана — `Docs/Tasks/`; если в проекте уже есть `docs/`, план лежит в `docs/Tasks/` (регистр не важен). План плагина узнаётся по доске `Board.md`, которую пишет скрипт: папку `docs/tasks` без такой доски хуки и команды считают чужой и не трогают.

## 3. Типы

| Тип | Где лежит | ID | Когда использовать |
|-----|-----------|----|-------------------|
| `epic` | своя папка в корне плана | `E-01` | Крупная цель или этап (MVP, релиз, большая подсистема). Состоит из фич. |
| `feature` | своя папка в папке эпика | `F-03` | Законченная возможность, которую можно показать. Состоит из задач. |
| `task` | в папке своей фичи | `F03-02` | Работа, которую один агент делает за одну-две сессии. |
| `research` | в папке своей фичи | `F03-02` | Нужно сначала выбрать решение. Результат — ADR; реализация — отдельная задача, зависящая от research. |
| `bug` | в папке своей фичи | `F03-02` | Что-то работает не так, как описано. |
| `idea` | `Backlog/` | `I-001` | Мысль «на потом». Не в плане, не блокирует, не имеет зависимостей. |
| `adr` | `Adr/` | `ADR-001` | Принятое решение с обоснованием. |

## 4. Имена файлов и ID

- **Эпики `E-01` и фичи `F-03`** нумеруются сквозь весь план. Номер — не меньше двух цифр (`F-100` после `F-99`).
- **Задачи** (`task`, `research`, `bug`) нумеруются **внутри своей фичи**: `F03-01`, `F03-02` … — номер фичи без дефиса и два знака. По ID сразу видно фичу; номер не разрастается до тысяч. В фиче — не больше 99 задач; больше — фичу нужно разбить.
- **Идеи `I-001` и ADR `ADR-001`** — сквозные, три цифры.
- Имя файла: `<ID> <Короткое название>.md`, например `F03-02 Койот-тайм для прыжка.md`. Заголовок `# ` внутри совпадает с именем файла. Ссылка — по полному имени: `[[F03-02 Койот-тайм для прыжка]]`.
- **ID выдаётся один раз и навсегда:** следующий номер = максимальный существующий + 1 (с учётом `cancelled`, `done` и прежних ID перенесённых задач — поле `former_ids`). Номера не переиспользуются, дыры не заполняются. ID выдаёт скрипт: `tasks.mjs new` или `new-id`.
- **Перенос:** задача в другую фичу — `tasks.mjs move <ID> --to <F-ID>`: получает новый ID в целевой фиче, старый записывается в `former_ids` и в её журнал, ссылки во всём плане правятся; по старому ID задачу по-прежнему находят `show` и `set`. Журналы — история: ID в записях не переписываются. Фича в другой эпик — `move <F-ID> --to <E-ID>`: переезжает папкой, ID не меняются. Переносить можно только фичу, которая лежит в своей папке (иначе сначала `tasks.mjs migrate`).
- **Имя файла стабильно.** Переименовывать можно только вместе с правкой всех ссылок на него (в Obsidian это делается автоматически; агент обязан найти и поправить ссылки сам). Скрипт проверки ловит битые ссылки.
- Название — 2–6 слов, по сути работы, без слов «задача», «сделать».

## 5. Поля frontmatter

Порядок полей — как в таблицах. Ссылки в полях пишутся в кавычках: `"[[F-07 Прыжок]]"`.

### Общие для всех

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `id` | да | Совпадает с началом имени файла |
| `type` | да | `epic` \| `feature` \| `task` \| `research` \| `bug` \| `idea` \| `adr` |
| `status` | да | см. раздел 6 |
| `created` | да | `YYYY-MM-DD` |

### epic, feature

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `priority` | да | `must` \| `should` \| `could` |
| `parent` | feature — да | ссылка на эпик |

### task, research, bug

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `role` | нет | кто делает задачу — **свободная метка**, любое слово латиницей строчными: `programmer`, `gamedesigner`, `artist`, `qa`, имя агента… Список ролей не фиксирован. Нужна, чтобы видеть исполнителя на доске и выбирать задачи по нему (`/task:next --role gamedesigner`) |
| `priority` | да | `must` \| `should` \| `could` |
| `size` | да | `XS` \| `S` \| `M` \| `L`. Больше `L` не бывает — такую задачу надо разбить или сделать фичей |
| `parent` | да | ссылка на фичу |
| `depends_on` | да | список ссылок на задачи, которые должны быть `done` раньше; пустой — `[]` |
| `sprint` | нет | `S-01`, `S-02` … — в какую итерацию взята |
| `former_ids` | нет | прежние ID задачи: `[F01-03]`. Ставят `move` и `migrate`, руками не правится; эти номера больше не выдаются |

### idea

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `promoted_to` | нет | ссылка на задачу/фичу, в которую превратилась идея |

### adr

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `task` | нет | ссылка на research-задачу, в которой принято решение |
| `superseded_by` | нет | ссылка на ADR, который заменил этот |

Пример задачи:

```yaml
---
id: F03-02
type: task
role: gamedesigner
status: ready
priority: must
size: S
parent: "[[F-03 Прыжок]]"
depends_on:
  - "[[F03-01 Гравитация и падение]]"
sprint: S-03
created: 2026-10-01
---
```

## 6. Статусы

### task, research, bug

| Статус | Значит |
|--------|--------|
| `draft` | Задача записана, но ещё не готова к работе: не хватает деталей или критериев |
| `ready` | Понятно, что делать и как проверить; можно брать, когда закрыты зависимости |
| `in-progress` | Агент или человек сейчас работает над ней |
| `review` | Работа сделана, нужна проверка человеком (например, руками в игре) |
| `done` | Готово и проверено |
| `cancelled` | Больше не нужна; причина — в журнале |

Переходы: `draft → ready → in-progress → review → done`; `review → in-progress` (вернули на доработку); `in-progress → ready` (отложили, причина в журнале); из любого — в `cancelled`.

**`blocked` не хранится.** Задача заблокирована, если хоть одна из `depends_on` не `done` — это вычисляется. Задачу с незакрытыми зависимостями в `in-progress` не берут.

- Зависимость, которой нет в плане (битая ссылка), тоже блокирует — пока ссылку не поправят.
- Отменённая зависимость (`cancelled`) задачу не разблокирует: её убирают из `depends_on` или заменяют. `check` об этом предупреждает, а `set <ID> cancelled` перечисляет задачи, которые ждали отменённую.
- **Закрытая фича или эпик (`done` или `cancelled`) — закрыты для задач.** Новую задачу или фичу в них не заводят (`new`), открытую не переносят (`move`), закрытую внутри не открывают снова (`set` в `draft`, `ready`, `in-progress`, `review`) — скрипт откажет. Нужно — сначала открой родителя (`set <F-ID> in-progress`) или выбери открытую фичу.
- **Фичу или эпик не закрывают, пока внутри есть открытые задачи или фичи**: `set <F-ID> done` (и `cancelled`) откажет со списком — сначала закрой, отмени или перенеси их (`move`).
- `check` считает открытую задачу в закрытом родителе ошибкой (`parent-closed`).

### epic, feature

`draft` → `ready` → `in-progress` → `done` (+ `cancelled`). Фича `in-progress`, когда в работе хоть одна её задача; `done` — когда все задачи `done`/`cancelled`.

### idea

`idea` → `done` (взята в план, заполнен `promoted_to`) или `cancelled`.

### adr

`proposed` → `accepted` → (`superseded`, заполнен `superseded_by`).

## 7. Тело файла

### Блок «Коротко» — обязателен для всех типов

Цитата сразу под заголовком. Каждая строка — одно предложение, понятное без остального файла.

| Тип | Строки |
|-----|--------|
| epic, feature, task, research, bug | **Что** · **Зачем** · **Готово, когда** |
| idea | **Что** · **Зачем** |
| adr | **Решение** · **Почему** · **Следствия** |

```markdown
# F03-02 Койот-тайм для прыжка

> **Что:** прыжок разрешён ещё 0.1 с после схода с края.
> **Зачем:** прыжки с платформ ощущаются честными.
> **Готово, когда:** прыжок срабатывает в окне, тест окна зелёный.
```

«Готово, когда» — проверяемое условие, а не «сделано хорошо».

### Разделы по типам

| Тип | Разделы (в этом порядке) |
|-----|--------------------------|
| task, research | Критерии готовности · Детали · Проверка · Журнал |
| bug | Воспроизведение · Критерии готовности · Детали · Проверка · Журнал |
| feature | Входит · Не входит · Принятые решения · Журнал |
| epic | Цель · MVP · После MVP · Журнал |
| idea | — (только «Коротко»; можно пару строк текста) |
| adr | Контекст · Решение · Отвергнутые варианты |

- **Критерии готовности** — чекбоксы `- [ ]`. Каждый пункт проверяем. У задачи в `ready` их не может не быть; пустой пункт `- [ ]` и пункт из одной подсказки шаблона критерием не считаются.
- **Детали** — любой объём: всё, что нужно исполнителю, чтобы сделать задачу без переспрашиваний (раздел 8).
- **Проверка** — как убедиться, что критерии выполнены: команды, сценарии, что открыть и посмотреть.
- **Журнал** — последний раздел, записи только добавляются (раздел 9).
- Необязательный раздел можно опустить, если в нём нечего писать. «Коротко» и «Журнал» не опускаются (кроме idea и adr, где журнала нет).

Заголовки разделов пишутся ровно так, как в таблице раздела 11, — по ним работают скрипт и команды.

### Шаблоны

Новый файл создаётся **скриптом**, а не вручную и не по памяти: `node "${CLAUDE_PLUGIN_ROOT}/scripts/tasks.mjs" new <тип> --title "…" --parent <ID> …` — он выдаёт ID (для задачи — внутри фичи), кладёт файл в папку родителя и заполняет frontmatter из шаблона `${CLAUDE_PLUGIN_ROOT}/templates/<тип>.md`. Тело — «Коротко», критерии и остальное — пишешь ты, вместо подсказок `<!-- … -->`, которые при заполнении удаляются.

## 8. Как написать хорошую задачу

Правила одинаковы для задач любого исполнителя.

- **«Коротко» понятен без остального файла.** Человек, открывший задачу впервые, за несколько секунд понимает, что делаем и зачем.
- **Критерий — проверяемое утверждение о результате**, а не шаг работы и не оценка:
  - ✓ «Персонаж перепрыгивает препятствие в 2 м и не перепрыгивает 3 м»
  - ✓ «Сборка проходит без ошибок; тест X зелёный»
  - ✗ «Написан класс JumpComponent» — это шаг, а не результат
  - ✗ «Прыжок приятный» — не проверяемо; сформулируй, по чему это видно
- **Если результат можно проверить только руками** (в игре, в редакторе, глазами) — это отдельный критерий, и задача закрывается через `review`: окончательное «да» даёт человек.
- **«Детали» отвечают на вопросы исполнителя заранее**: на что опираться (ссылки на ADR, задачи, документы), что затронуто, ограничения, открытые вопросы. Объём любой.
- **Чем точнее задание, тем лучше результат.** Исполнитель — особенно агент — делает то, что требуют, а «Зачем» читает как пожелание: недосказанное он трактует минимально, и критерии выполняются формально, а цель задачи — нет. Поэтому переводи цель в **требования к результату** — в критериях или нумерованным списком в «Деталях», каждое проверяемо (тестом, командой, сценарием):
  - **гарантия, а не частный случай** — «работает всегда / в любом режиме / при любом порядке», и назови случаи, где это легко ломается;
  - **отказ при нарушении** — что проверка (тест, линтер, сборка) отклоняет и с каким сообщением, иначе нарушение пройдёт незамеченным;
  - **одно место** — формат, константа, правило задаётся один раз и используется везде, где нужен;
  - **документы** — что обновить вместе с работой.
  - ✓ цель «по копии можно узнать, откуда она утекла» → требования «метка есть в любой сборке; упаковка без метки — ошибка; формат метки задан в одном месте»
  - ✗ «метка в коде сборки» — выполнимо так, что метка окажется только в частном случае

  Требования — о результате, а не о способе: «как» выбирает исполнитель.
- **«Проверка» — конкретные действия**: что запустить или открыть, куда смотреть, что должно получиться.
- **Размер — не больше `L`.** Задачу, которую не сделать за одну-две сессии, разбей или сделай фичей.
- **Если сначала нужно выбрать решение** — отдельная `research`-задача с ADR, а реализация зависит от неё.

## 9. Как агент работает с системой (обязательно)

Раздел для любого агента, который создаёт задачи или работает по ним.

### Сориентироваться

- План лежит в `Docs/Tasks/`. Начни с `Board.md`: что готово к работе, что в работе, что заблокировано.
- Задачу понимай по «Коротко», затем читай критерии и детали, затем журнал — там может быть важный контекст от предыдущих исполнителей.
- Задача готова к работе, если она `ready` и все её `depends_on` — `done`.
- **Задачи берутся по порядку плана**: из готовых — первая в очереди (`tasks.mjs next`): текущий спринт, затем по ID. Не перескакивай на другую задачу по своему усмотрению; хочешь поменять порядок — предложи человеку.

### Создать задачу, фичу, идею

1. Проверь, нет ли уже такой задачи или идеи.
2. Создай файл скриптом `tasks.mjs new` (раздел 7, «Шаблоны») — он сам выдаст ID и положит файл в папку родителя — и заполни тело.
3. Заполни `parent`, `depends_on` и, если нужно, `role` — кто будет делать.
4. Пока задача не описана до конца — `draft`; когда есть критерии и понятно, как проверить, — `ready`.
5. Задачу, которую не просили создать, сначала предложи человеку. Мысль «на потом» — идея в `Backlog/`: её можно записать без согласования.

### Вести задачу

1. **Взял** — сразу `status: in-progress` и запись в журнал «взята в работу»: `tasks.mjs set <ID> in-progress --log "взята в работу."`. Не бери задачу, у которой не закрыты `depends_on`. Один агент — одна задача `in-progress` одновременно. Скрипт запоминает, какая сессия взяла задачу: если она закончит ответ, не оставив в журнале итог или место остановки, хук напомнит. Продолжаешь свою задачу в новой сессии — добавь `--take`.
2. **Работаешь** — значимые решения, находки и отклонения от плана пиши в журнал по ходу, а не в конце.
3. **Закончил** — отметь выполненные критерии `[x]`; невыполненный пункт оставь `[ ]` и объясни в журнале. Если пункт сознательно снят или перенесён в другую задачу — зачеркни его и укажи куда: `- [ ] ~~Диалог проверен человеком~~ → перенесено в [[F05-01 …]]`; такой пункт больше не считается открытым. Статус `done` (или `review`, если нужна проверка человеком) + итоговая запись: что сделано, где результат, что изменилось в плане.
4. **Упёрся или отложил** — запись в журнале с причиной; статус `ready` (отложил) или оставить `in-progress` с описанием, чего ждёшь.
5. **Статус и журнал меняются в том же шаге, что и работа** — не «потом», не «в конце сессии».
6. **Не меняй молча чужие задачи.** Если выяснилось, что будущие задачи надо поправить — предложи правки человеку; после подтверждения внеси их и оставь запись в журнале каждой изменённой задачи со ссылкой на причину.
7. **Не расширяй задачу молча.** Новая работа — новая задача (с подтверждения) или идея в `Backlog/`.
8. **Критерии готовности меняются только с записью в журнале** — почему изменились.

### Запись журнала

```markdown
- **2026-10-01 · programmer (Claude):** что сделано / что решено / что изменилось в плане.
```

Дата · кто (роль или имя агента, в скобках — кто именно) · текст. Новые записи — внизу. Длинные подробности — вложенным списком под записью.

Как передать текст скрипту (`tasks.mjs set … --log`), чтобы оболочка его не испортила:

- короткий текст без обратных кавычек, `$` и двойных кавычек — `--log "…"`;
- текст с Markdown — через stdin, `--log -`. В bash — here-doc с кавычками вокруг `EOF` (без них оболочка выполнит `код` в обратных кавычках и подставит `$…`):

  ```
  tasks.mjs set <ID> done --log - <<'EOF'
  готово: поправлен `parseArgs`.
  - результат: `plugin/scripts/tasks.mjs`, тесты зелёные.
  EOF
  ```

  Строки после первой скрипт сам оформит вложенным списком;
- в PowerShell here-doc нет, а обратная кавычка — спецсимвол: допиши запись в «Журнал» правкой файла и вызови `set` без `--log` (или передай текст файлом: `--log-file <путь>`).

## 10. Доска и проверка

- `Board.md` генерируется скриптом плагина и командой `/task:board`; ручные правки перезаписываются.
- На доске и в любых списках задач задачи идут **по порядку ID**. В колонке «Ждёт» — только незакрытые зависимости, ссылками с коротким именем: `[[F02-02 Каркас и локальная установка|F02-02]]` (внутри таблицы `|` экранируется: `\|`).
- Скрипт проверяет: циклы в `depends_on`, битые ссылки (вложения — картинки, pdf — считаются, если файл есть в плане; ссылки в коде — нет), дубли ID и имён файлов, несовпадение ID и имени файла, неизвестные типы и статусы, отсутствие обязательных полей и `parent`, пустой «Коротко», оставшиеся подсказки шаблона, `ready` без критериев, `done` с неотмеченными критериями, `done`/`review` без записи в журнале, `in-progress` с незакрытыми зависимостями, зависимость от отменённой задачи, открытую задачу в закрытой фиче или эпике.
- После правки файла плана хук сообщает агенту только ошибки, связанные с этой правкой; давние ошибки в чужих задачах исправляются только по просьбе человека.

## 11. Заголовки разделов

Скрипт и команды узнают разделы по этим заголовкам — пиши их без изменений. «Коротко» узнаётся по положению — первая цитата после заголовка `# `.

| Где | Заголовки |
|-----|-----------|
| «Коротко» (epic, feature, task, research, bug) | **Что:** / **Зачем:** / **Готово, когда:** |
| «Коротко» (idea) | **Что:** / **Зачем:** |
| «Коротко» (adr) | **Решение:** / **Почему:** / **Следствия:** |
| task, research, bug | `## Критерии готовности`, `## Детали`, `## Проверка`, `## Журнал` |
| bug | `## Воспроизведение` |
| feature | `## Входит`, `## Не входит`, `## Принятые решения` |
| epic | `## Цель`, `## MVP`, `## После MVP` |
| adr | `## Контекст`, `## Решение`, `## Отвергнутые варианты` |
