# Формат плана задач

Единственный источник правил для людей, агентов, команд `/task:*` и скрипта проверки. Если правило здесь не описано — его нет.

## 1. Главные принципы

1. **Задачу понимают за несколько секунд.** Сразу под заголовком — блок «Коротко». Подробности любого объёма — ниже.
2. **У каждого факта одно место.** Зависимость пишется только в `depends_on` задачи-потребителя; принадлежность — только в `parent` ребёнка. Обратные связи, списки детей и доска вычисляются.
3. **Статус всегда правдив.** Агент, работающий по задаче, обновляет статус и журнал сразу, в том же шаге, что и работу (раздел 8).
4. **Чистый Markdown.** План читается в Obsidian без плагинов; связи — вики-ссылки `[[...]]`.
5. **Поля — по-английски, содержимое — на языке пользователя.** Язык плана записан в `Docs/Tasks/Readme.md` (поле `language`).

## 2. Раскладка

```
Docs/Tasks/
├── Readme.md      ← что это за папка, язык плана, ссылка на этот формат
├── Board.md       ← доска; генерируется, руками не править
├── Epics/         ← E-01 …
├── Features/      ← F-01 …
├── Tasks/         ← T-001 … (типы task, research, bug)
├── Backlog/       ← I-001 … (идеи)
├── Adr/           ← ADR-001 … (решения, результат research)
└── Roles/         ← необязательно: профили ролей проекта
```

Имена папок и служебных файлов — UpperCamelCase. Задача не переезжает между папками при смене статуса или спринта: папка определяется только типом.

## 3. Типы

| Тип | Папка | Префикс ID | Когда использовать |
|-----|-------|-----------|-------------------|
| `epic` | `Epics/` | `E-01` | Крупная цель или этап (MVP, релиз, большая подсистема). Состоит из фич. |
| `feature` | `Features/` | `F-01` | Законченная возможность, которую можно показать. Состоит из задач. |
| `task` | `Tasks/` | `T-001` | Работа, которую один агент делает за одну-две сессии. |
| `research` | `Tasks/` | `T-001` | Нужно сначала выбрать решение. Результат — ADR; реализация — отдельная задача, зависящая от research. |
| `bug` | `Tasks/` | `T-001` | Что-то работает не так, как описано. |
| `idea` | `Backlog/` | `I-001` | Мысль «на потом». Не в плане, не блокирует, не имеет зависимостей. |
| `adr` | `Adr/` | `ADR-001` | Принятое решение с обоснованием. |

`task`, `research` и `bug` делят одну нумерацию `T-`.

## 4. Имена файлов и ID

- Имя файла: `<ID> <Короткое название>.md`, например `T-042 Койот-тайм для прыжка.md`. Заголовок `# ` внутри совпадает с именем файла.
- Ссылка на задачу — по полному имени: `[[T-042 Койот-тайм для прыжка]]`.
- **ID выдаётся один раз и навсегда:** следующий номер = максимальный существующий номер этого префикса + 1 (с учётом `cancelled` и `done`). Номера не переиспользуются, дыры не заполняются.
- Ширина номера: `E-`/`F-` — две цифры, `T-`/`I-`/`ADR-` — три.
- **Имя файла стабильно.** Переименовывать можно только вместе с правкой всех ссылок на него (в Obsidian это делается автоматически; агент обязан найти и поправить ссылки сам). Скрипт проверки ловит битые ссылки.
- Название — 2–6 слов, по сути работы, без слов «задача», «сделать».

## 5. Поля frontmatter

Порядок полей — как в таблицах. Ссылки в полях пишутся в кавычках: `"[[F-07 Прыжок]]"`.

### Общие для всех

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `id` | да | Совпадает с началом имени файла |
| `type` | да | `epic` \| `feature` \| `task` \| `research` \| `bug` \| `idea` \| `adr` |
| `status` | да | см. раздел 6 |
| `created` | да | `YYYY-MM-DD` |

### epic, feature

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `priority` | да | `must` \| `should` \| `could` |
| `parent` | feature — да | ссылка на эпик |

### task, research, bug

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `role` | да | роль исполнителя: `programmer`, `architect`, `gamedesigner`, `devops` или роль из `Roles/` |
| `priority` | да | `must` \| `should` \| `could` |
| `size` | да | `XS` \| `S` \| `M` \| `L`. Больше `L` не бывает — такую задачу надо разбить или сделать фичей |
| `parent` | да | ссылка на фичу |
| `depends_on` | да | список ссылок на задачи, которые должны быть `done` раньше; пустой — `[]` |
| `sprint` | нет | `S-01`, `S-02` … — в какую итерацию взята |

### idea

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `promoted_to` | нет | ссылка на задачу/фичу, в которую превратилась идея |

### adr

| Поле | Обяз. | Значения |
|------|:-----:|----------|
| `task` | нет | ссылка на research-задачу, в которой принято решение |
| `superseded_by` | нет | ссылка на ADR, который заменил этот |

Пример задачи:

```yaml
---
id: T-042
type: task
role: gamedesigner
status: ready
priority: must
size: S
parent: "[[F-07 Прыжок]]"
depends_on:
  - "[[T-040 Гравитация и падение]]"
sprint: S-03
created: 2026-10-01
---
```

## 6. Статусы

### task, research, bug

| Статус | Значит |
|--------|--------|
| `draft` | Задача записана, но ещё не готова к работе: не хватает деталей или критериев |
| `ready` | Понятно, что делать и как проверить; можно брать, когда закрыты зависимости |
| `in-progress` | Агент или человек сейчас работает над ней |
| `review` | Работа сделана, нужна проверка человеком (например, руками в игре) |
| `done` | Готово и проверено |
| `cancelled` | Больше не нужна; причина — в журнале |

Переходы: `draft → ready → in-progress → review → done`; `review → in-progress` (вернули на доработку); `in-progress → ready` (отложили, причина в журнале); из любого — в `cancelled`.

**`blocked` не хранится.** Задача заблокирована, если хоть одна из `depends_on` не `done` — это вычисляется. Задачу с незакрытыми зависимостями в `in-progress` не берут.

### epic, feature

`draft` → `ready` → `in-progress` → `done` (+ `cancelled`). Фича `in-progress`, когда в работе хоть одна её задача; `done` — когда все задачи `done`/`cancelled`.

### idea

`idea` → `done` (взята в план, заполнен `promoted_to`) или `cancelled`.

### adr

`proposed` → `accepted` → (`superseded`, заполнен `superseded_by`).

## 7. Тело файла

### Блок «Коротко» — обязателен для всех типов

Цитата сразу под заголовком. Каждая строка — одно предложение, понятное без остального файла.

| Тип | Строки |
|-----|--------|
| epic, feature, task, research, bug | **Что** · **Зачем** · **Готово, когда** |
| idea | **Что** · **Зачем** |
| adr | **Решение** · **Почему** · **Следствия** |

```markdown
# T-042 Койот-тайм для прыжка

> **Что:** прыжок разрешён ещё 0.1 с после схода с края.
> **Зачем:** прыжки с платформ ощущаются честными.
> **Готово, когда:** прыжок срабатывает в окне, тест окна зелёный.
```

«Готово, когда» — проверяемое условие, а не «сделано хорошо».

### Разделы по типам

| Тип | Разделы (в этом порядке) |
|-----|--------------------------|
| task, research | Критерии готовности · Детали · Проверка · Журнал |
| bug | Воспроизведение · Критерии готовности · Детали · Проверка · Журнал |
| feature | Входит · Не входит · Принятые решения · Журнал |
| epic | Цель · MVP · После MVP · Журнал |
| idea | — (только «Коротко»; можно пару строк текста) |
| adr | Контекст · Решение · Отвергнутые варианты |

- **Критерии готовности** — чекбоксы `- [ ]`. Каждый пункт проверяем. У задачи в `ready` их не может не быть.
- **Детали** — любой объём: архитектура, шаги, ссылки на код и ADR, открытые вопросы. Что писать, зависит от роли (профили ролей).
- **Проверка** — как убедиться, что критерии выполнены: команды, сценарии, что открыть и посмотреть.
- **Журнал** — последний раздел, записи только добавляются (раздел 8).
- Необязательный раздел можно опустить, если в нём нечего писать. «Коротко» и «Журнал» не опускаются (кроме idea и adr, где журнала нет).

Заголовки разделов пишутся на языке плана. Для других языков — таблица в разделе 10.

## 8. Как агент ведёт задачу (обязательно)

1. **Взял** — сразу `status: in-progress` и запись в журнал «взята в работу». Не бери задачу, у которой не закрыты `depends_on`. Одна роль/агент — одна задача `in-progress` одновременно.
2. **Работаешь** — значимые решения, находки и отклонения от плана пиши в журнал по ходу, а не в конце.
3. **Закончил** — отметь выполненные критерии `[x]`; невыполненный пункт оставь `[ ]` и объясни в журнале. Статус `done` (или `review`, если нужна проверка человеком) + итоговая запись: что сделано, где результат, что изменилось в плане.
4. **Упёрся или отложил** — запись в журнале с причиной; статус `ready` (отложил) или оставить `in-progress` с описанием, чего ждёшь.
5. **Статус и журнал меняются в том же шаге, что и работа** — не «потом», не «в конце сессии».
6. **Не меняй молча чужие задачи.** Если выяснилось, что будущие задачи надо поправить — предложи правки человеку; после подтверждения внеси их и оставь запись в журнале каждой изменённой задачи со ссылкой на причину.
7. **Не расширяй задачу молча.** Новая работа — новая задача (с подтверждения) или идея в `Backlog/`.
8. **Критерии готовности меняются только с записью в журнале** — почему изменились.

### Запись журнала

```markdown
- **2026-10-01 · programmer (Claude):** что сделано / что решено / что изменилось в плане.
```

Дата · роль (кто) · текст. Новые записи — внизу. Длинные подробности — вложенным списком под записью.

## 9. Доска и проверка

- `Board.md` генерируется скриптом плагина и командой `/task:board`; ручные правки перезаписываются.
- Скрипт проверяет: циклы в `depends_on`, битые ссылки, дубли ID, несовпадение ID и имени файла, неизвестные типы и статусы, отсутствие обязательных полей и `parent`, пустой «Коротко», `ready` без критериев, `done` с неотмеченными критериями без пояснения, `done`/`review` без записи в журнале, `in-progress` с незакрытыми зависимостями.

## 10. Заголовки на других языках

Скрипт и команды узнают разделы по этим заголовкам. «Коротко» узнаётся по положению — первая цитата после заголовка `# `.

| Ключ | ru | en |
|------|----|----|
| what / why / done-when | Что / Зачем / Готово, когда | What / Why / Done when |
| decision / reason / consequences | Решение / Почему / Следствия | Decision / Why / Consequences |
| criteria | Критерии готовности | Acceptance criteria |
| details | Детали | Details |
| verification | Проверка | Verification |
| log | Журнал | Log |
| repro | Воспроизведение | Reproduction |
| in-scope / out-of-scope | Входит / Не входит | In scope / Out of scope |
| decisions | Принятые решения | Decisions |
| goal / mvp / after-mvp | Цель / MVP / После MVP | Goal / MVP / After MVP |
| context / alternatives | Контекст / Отвергнутые варианты | Context / Rejected alternatives |
