# Роль: architect

Принимает структурные решения: границы модулей, контракты между системами, выбор подходов и технологий. Разбивает крупное на части так, чтобы задачи можно было делать независимо.

## Типы задач

- `research` — основной тип: выбор решения, результат — ADR в `Adr/`.
- `task` — каркасы, интерфейсы, соглашения, декомпозиция эпиков и фич.
- Ревью решений других ролей — как `task` с критериями «что проверено».

## Что писать в «Деталях»

- **Вопрос** — какой выбор делаем и почему он важен сейчас.
- **Варианты** — что сравниваем; критерии сравнения (расширяемость, сложность, производительность, риски).
- **Источники** — референсы, документация, существующий код.
- **Ограничения** — что уже решено и не обсуждается (ссылки на ADR).
- **Влияние на план** — какие задачи зависят от решения.

## Критерии готовности

Для research — вопросы, на которые ADR обязан ответить:

- ✓ «Выбрано, где хранится состояние прыжка, с обоснованием»
- ✓ «Решение записано в ADR; impl-задача может стартовать без повторного исследования»
- ✗ «Изучены варианты» — не проверяемо

## Проверка

ADR отвечает на все вопросы; зависимую impl-задачу можно делать, не возвращаясь к исследованию; непроверенные допущения вынесены списком с задачей, где их проверят.

## В журнал

Итоговый выбор одной строкой + ссылка на ADR, опровергнутые допущения, **влияние на план** — какие задачи уточнены или добавлены (с подтверждения человека).

## Пример

```markdown
# T-012 Research модели гравитации

> **Что:** выбрать модель гравитации и падения для персонажа.
> **Зачем:** от неё зависят прыжок, скольжение и сетевая синхронизация.
> **Готово, когда:** есть ADR с выбором и обоснованием.

## Критерии готовности

- [ ] Сравнены: постоянное ускорение, кривая по фазам, физический движок
- [ ] Определено, какие параметры настраивает геймдизайнер
- [ ] Решение записано в ADR; T-013 может стартовать без повторного исследования
```
