# Роль: programmer

Пишет и меняет код: реализует механики, системы, инструменты, исправляет ошибки. Работает по решениям архитектора (ADR) и описаниям геймдизайнера.

## Типы задач

- `task` — реализация; основной тип.
- `bug` — исправление.
- `research` — только короткий технический выбор внутри своей зоны (библиотека, приём реализации). Архитектурные развилки — роль architect.

## Что писать в «Деталях»

- **Опора** — ADR, спецификация механики, задачи-предшественники: ссылками.
- **Затронутые файлы** — таблица «действие · путь» (создать / изменить / удалить).
- **Шаги** — порядок реализации, если он не очевиден.
- **Ограничения** — что нельзя трогать, соглашения проекта, производительность, сеть.
- **Открытые вопросы** — что выяснить по ходу; ответы потом — в журнал.

## Критерии готовности

Проверяемые утверждения о поведении и качестве, не о «написанном коде»:

- ✓ «Персонаж прыгает в течение 0.1 с после схода с края»
- ✓ «Сборка без ошибок и предупреждений; тесты X и Y зелёные»
- ✗ «Написан класс JumpComponent» — это шаг, а не результат

Если часть проверить можно только руками (в редакторе, в игре) — отдельный пункт, и задача закрывается в `review`, а не в `done`.

## Проверка

Команды сборки и тестов, сценарий ручной проверки: что запустить, куда смотреть, что должно произойти.

## В журнал

Что сделано и где (файлы, коммиты), отклонения от ADR и почему, найденные подводные камни, что осталось непроверенным.

## Пример

```markdown
# T-042 Койот-тайм для прыжка

> **Что:** прыжок разрешён ещё 0.1 с после схода с края.
> **Зачем:** прыжки с платформ ощущаются честными.
> **Готово, когда:** прыжок срабатывает в окне, тест окна зелёный.

## Критерии готовности

- [ ] Прыжок проходит в течение `CoyoteTime` после потери опоры, после — нет
- [ ] `CoyoteTime` настраивается, по умолчанию 0.1 с
- [ ] Автотест на границы окна зелёный
- [ ] Ощущение проверено руками в тестовой карте
```
