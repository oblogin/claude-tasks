# F09-01 Проверка переходов в set

> **Что:** `tasks.mjs set` разрешает только переходы статусов из спецификации (раздел 6 `task:format`) и отказывает в остальных без `--force`.
> **Зачем:** сейчас можно, например, поставить `done` задаче из `draft`, минуя работу и журнал, — план перестаёт быть правдивым.
> **Готово, когда:** недопустимый переход отклоняется с понятным сообщением, допустимые и законные сценарии плагина проходят, тесты зелёные.

## Критерии готовности

- [ ] Таблица допустимых переходов задана в `tasks.mjs` в одном месте отдельно для каждой группы типов (task/research/bug, epic/feature, idea, adr), и `set` проверяет по ней каждый вызов
- [ ] Недопустимый переход без `--force` отклоняется: код выхода не 0, файл не меняется, в ответе `code: 'bad-transition'` и сообщение вида «draft → done недопустим для task; можно: ready, cancelled. Всё равно — с --force»
- [ ] С `--force` недопустимый переход проходит, и в журнал задачи пишется пометка о принудительном переходе (даже без `--log`)
- [ ] Законные сценарии проходят без `--force` (список — в «Деталях», пункт 2); на каждый есть тест
- [ ] На каждую группу типов — тест хотя бы на один недопустимый переход
- [ ] Остальные проверки `set` (незакрытые зависимости, закрытый родитель, открытые дети) работают как раньше; все тесты плагина зелёные
- [ ] Обновлены: раздел 6 `plugin/skills/format/SKILL.md` (переходы проверяет скрипт, обход — `--force`), справка `set` в USAGE, README; скилы `next`, `done`, `replan`, `board` не советуют переходов, которые теперь отклоняются
- [ ] Версия плагина поднята

## Детали

Идея — [[I-005 Строгие переходы статусов]], найдена при саморевью ([[F07-01 Дефекты из саморевью]]). Код — `setStatus` в `plugin/scripts/tasks.mjs`, проверку ставить рядом с проверкой допустимого статуса (до записи файла).

Требования к результату:

1. **Таблица переходов — из спецификации, раздел 6:**
   - task/research/bug: `draft → ready`, `ready → in-progress`, `in-progress → review`, `in-progress → done`, `review → done`, `review → in-progress`, `in-progress → ready`, любой → `cancelled`;
   - epic/feature: `draft → ready → in-progress → done` + любой → `cancelled`;
   - idea: `idea → done`, `idea → cancelled`;
   - adr: `proposed → accepted`, `accepted → superseded` (и `proposed → superseded`, если ADR отвергнут до принятия — решить и записать в журнал).
2. **Законные сценарии, которые не должны требовать `--force`** (иначе агенты начнут ставить `--force` всегда и проверка обесценится):
   - тот же статус → тот же статус — запись в журнал без смены статуса (так делает `/task:replan`);
   - `in-progress → done` без `review` (`/task:done` закрывает так, если проверка человеком не нужна);
   - переоткрыть закрытого родителя: фича/эпик `done → in-progress` (скилы `next`, `board` и раздел 6 спецификации прямо это советуют);
   - фича/эпик `draft → in-progress` и `ready → in-progress` — фича становится `in-progress`, когда в работе хоть одна её задача;
   - вернуть задачу на доработку после `done` (`done → in-progress`) — решить: разрешать без `--force` или только с ним; решение записать в журнал и в спецификацию.
3. **Отказ — понятный**: какой переход, для какого типа, какие статусы допустимы отсюда, как обойти.
4. **Одно место**: таблица переходов — одна константа; спецификация описывает те же переходы, расхождение — дефект.

Открытый вопрос (решить в работе и записать в журнал): нужно ли `check` предупреждать о задачах, чей текущий статус недостижим из истории журнала, — скорее нет, это вне задачи.

## Проверка

1. `node --test plugin/scripts/test/*.test.mjs` — все тесты зелёные, среди них новые тесты переходов.
2. Во временной копии плана: `tasks.mjs set <draft-задача> done` → отказ с `bad-transition`, файл не изменился; то же с `--force` → статус `done`, в журнале пометка о принудительном переходе.
3. `tasks.mjs set <задача> in-progress --log "…"` для задачи в `in-progress` — проходит (запись без смены статуса).
4. `node plugin/scripts/tasks.mjs check` на плане репозитория и на `examples/guess-number` — без ошибок.
